# ITEMX CODEX 2.1.1 → 2.2.0 구조 개선

사용자가 보는 기능은 거의 그대로다. 바뀐 것은 저장 구조의 안전장치와, 같은 것을 여러 곳에
베껴 두던 정의들을 한 곳으로 모은 것이다.

## 데이터 보호

- **체크포인트 마이그레이션.** 저장된 체크포인트 버전이 낮으면 현재 형식으로 올려서 계속 쓴다.
  이전에는 알 수 없는 버전을 만나면 체크포인트를 버리고 메시지 본문부터 재생을 시도했는데,
  압축이 그 구간의 마커를 이미 지운 뒤라 인벤토리·스킬·조우가 통째로 사라질 수 있었다.
- **읽기 전용 동결.** 그래도 읽지 못하는 체크포인트를 만나면 채팅을 잠근다. 화면 조회와
  백업 내보내기는 그대로 되고, 다시 봉인·수동 편집·보조 복구·저장소 최적화처럼 원장을
  다시 쓰는 경로만 거부한다. 백업 덮어쓰기로 복구할 수 있다.
- 잠긴 동안에는 인벤 화면 상단에 사유와 함께 배너가 뜬다.

## 오배송 차단

- 코덱스 전송 태그를 `DOMAINS` 레지스트리가 소유한다. 이전에는 `skill`로 시작하지 않는 모든
  태그가 조우(monster)로 처리됐다. 이제 등록되지 않은 태그는 어디에도 라우팅되지 않고
  본문에 그대로 남는다.

## 정의 단일화

- 아이템 필드를 `ITEM_FIELDS` 한 곳에서 선언한다. 전송 별칭, 잔여 태그 청소 정규식, 요청 앵커,
  백업 화이트리스트, 복구 품질 검증이 모두 여기서 파생된다. 이전에는 여섯 군데에 흩어져 있어
  하나를 빠뜨리면 조용히 깨졌다(태그가 본문에 노출되거나, 필드가 모든 백업에서 누락되거나).
- 프롬프트 문구와 백업 JSON 키 순서는 이전과 완전히 동일하게 유지된다.

## 빌드

- 스타일시트가 소스 파일이 됐다. 빌드가 더 이상 디자인 시안 HTML의 `<style>` 블록을 정규식으로
  긁어오지 않는다. 시안이 `src/`를 참조하는 방향으로 뒤집혔다.
- `src/shell.css`는 iframe 폴백 셸, `src/cards.css`는 카드 표면이다.

## 설정 화면 통합

설정 화면을 그리는 코드가 둘이었다. 화면 측면 드로어용 하나, 화면 권한을 받지 못한 환경의
iframe 폴백용 하나. 같은 화면을 두 번 적어 두었기 때문에 한쪽만 고쳐지는 일이 반복됐다.

- 2.0.23 — 밝은 스킨이 놓친 컨트롤 스킨 입히기
- 2.0.25 — 밝은 스킨에서 컨트롤이 검게 남던 문제
- 2.0.26 — iframe 폴백 설정을 드로어 디자인 수준으로

이제 `settingsPanelHtml()` 하나가 두 화면을 모두 그린다. 두 경로의 차이는 **조작을 연결하는
방식뿐**이다. 드로어는 클래스로 찾고, 폴백은 `data-action`으로 듣는다. 마크업·구성·문구는 공유한다.
양쪽의 바인딩 식별자는 기존 것을 그대로 두었으므로 라우터와 리스너는 손대지 않았다.

- 폴백이 드로어와 같은 카드·스위치·세그먼트·도메인 카드를 쓴다. 이전에는 더 단순한 구버전 모양이었다.
- 폴백에만 있던 문구 차이를 없앴다. (화면 스킨 설명, 봇 사용 설명, 저장 공간 문구)
- 드로어의 **백업 버튼에 버튼 스타일이 빠져 있던 것**을 고쳤다. 이전에는 아무 장식 없는 맨 버튼이었다.
- 설정 화면의 모든 버튼에 `type="button"`이 붙는다.
- 설정 표면 CSS를 `ITEMX_SETTINGS_STYLE` 하나로 모아 두 문서에 함께 넣는다. 드로어 전용으로 남는 것은
  탭을 여닫는 라디오 메커니즘뿐이다.
- 폴백 전용 설정 어휘(`.itemx-setting-card` 계열)를 배포본에서 들어냈다. 렌더하는 코드가 없는데 규칙만
  남아 있으면 다음 사람이 "폴백은 별도 스타일이 있다"고 읽고 다시 갈라진다.
- 정리하면서 **드로어 설정 카드의 제목과 설명에 스킨 규칙이 아예 없던 것**을 찾아 고쳤다. 밝은 스킨
  대응은 폴백 어휘에만 걸려 있었다.

드로어의 실제 렌더 결과를 리팩터 전후로 비교해 `type="button"` 추가와 클래스 나열 순서를 제외하면
**동일**함을 확인했다. 드로어 스타일시트 302개 규칙도 손실 없이 보존된다.

인벤·스킬·조우 탭 본문은 아직 통합하지 않았다. 드로어는 라디오 입력으로 CSS만으로 상세 페이지를
전환하고 폴백은 JS 상태로 전환한다. 탐색 방식 자체가 달라 별도 작업이 필요하다.

## 드로어 조작 디스패치

메인 문서는 좌표가 붙은 document 클릭 하나만 준다. 그래서 어느 컨트롤을 눌렀는지는 결국
hit test로 알아내야 한다. 문제는 그 hit test가 **손으로 쓴 `clientX >= rect.left && …` 4중 비교
22벌**이었다는 것이다. 컨트롤을 하나 추가하려면 450줄짜리 사슬 끝에 같은 블록을 또 붙여야 했다.

이제 설정 조작은 `rootSettingActions()` 표 한 곳에 있다. 한 행은 라우터가 찾을 클래스와 눌렀을 때
할 일이다. 라우터는 표를 한 번 훑는다.

```js
for (const action of rootSettingActions()) {
  if (!(await eventHitsMainClass(event, action.hook))) continue;
  await action.run();
  return;
}
```

- 라우터 784줄 → 312줄. 직접 쓴 좌표 비교 22 → 3 (남은 셋은 탭·페이저처럼 추가 데이터를 함께
  다루는 구조라 그대로 둔다).
- 디스패치 순서는 먼저 맞는 행이 이긴다. 순서 자체가 동작이므로 테스트로 고정했다.
- 모든 행이 `eventHitsMainClass`를 쓴다. 이 헬퍼는 `rect.width > 0 && rect.height > 0`을 확인하므로,
  접힌 `<details>` 안의 컨트롤처럼 크기가 0인 요소가 화면 원점 클릭에 한꺼번에 걸리던 가능성이
  사라졌다. 손으로 쓴 블록 대부분에는 이 확인이 없었다.

### 이전에는 할 수 없던 검사

렌더러가 내놓는 컨트롤과 라우터가 받는 컨트롤을 맞대볼 수 있게 됐다. 지금은 양방향으로 잠근다.

- 드로어가 그리는 모든 조작 클래스에 대응하는 행이 있는가
- 행이 가리키는 클래스를 실제로 누군가 그리는가

사슬이던 시절에는 렌더러만 고치고 분기를 빠뜨려도, 분기만 남기고 마크업을 바꿔도 사용자가
누르기 전까지 아무도 몰랐다.

## 화면

- iframe 폴백에 빠져 있던 **보조 모델 상태**와 **플러그인 버전** 카드를 추가했다.
  두 화면의 설정 항목이 어긋나지 않는지 테스트가 검사한다.

## 테스트

166 → 205. 체크포인트 마이그레이션·동결, 도메인 라우팅, 아이템 스키마 파생을 새로 잠갔다.
설정 화면 테스트는 소스 문자열이 아니라 실제 렌더 출력을 비교한다. 두 스킨이 같은 카드를 같은
순서로 내는지, 각 스킨이 자기 방식으로만 조작을 연결하는지, 설정 표면이 양쪽 문서에서
스타일링되는지를 검사한다.
